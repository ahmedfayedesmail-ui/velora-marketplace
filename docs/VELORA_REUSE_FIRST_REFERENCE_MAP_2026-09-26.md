PRIMARY BENCHMARK SOURCES REVIEWED\n\n- Shopify Admin: central hub with orders, products, customers, analytics/reports, marketing/promotions, discounts, and optional sales channels/apps.\n- Etsy Shop Manager: task-oriented dashboard with attention items, stats, orders, seller guidance/resources, and recent activity.\n- eBay Seller Hub: centralized orders, listings, performance, payouts, and store/marketing tools.\n- Spree Commerce: open-source core with marketplace seller onboarding, per-seller order splitting, commissions, payout ledger, React Admin, Seller Panel, and multi-region primitives.\n- Spree Storefront: open-source production storefront with one-page checkout, multi-shipment, coupon/gift-card support, customer accounts, SEO and multi-region routing.\n- Saleor: API-first/composable commerce, channels, promotions, payments, customer orders, returns and marketplace recipes.\n- Medusa: marketplace recipe using vendor models, vendor-authenticated routes, order-splitting workflows and customizable modules.\n- Spryker: merchant-aware catalog, split shipments/orders, merchant portal, marketplace Back Office, and merchant-scoped returns.\n- Vendure: promotion conditions/actions/constraints and an explicit Order state machine with aggregate/seller orders.\n- WooCommerce: fulfillment objects, partial fulfillment, tracking metadata, refunds, order notes, analytics, and revenue breakdowns.\n- Ulta AI: recommendations from beauty goals/concerns, product comparison, ingredient explanations, routine building, and gift guidance.\n- Sephora Beauty Insider: loyalty, savings, member benefits and ongoing customer relationship features.\n\n4. WHAT THE MATURE REFERENCES REPEATEDLY DO\n\nAdmin is an operating hub, not a collection of isolated screens.\nSeller Center is organized around tasks: onboarding → catalog → inventory → orders → fulfillment → returns → finance → performance → support.\nMarketplace orders keep the aggregate customer order while exposing merchant/seller context and shipment boundaries.\nFulfillment and shipment are separate from the customer order; tracking metadata hangs off fulfillment/shipment records.\nReturns are usually item-aware and merchant-aware, especially in marketplaces.\nRefunds are separate from physical returns and may be automatic via a gateway or manual for COD/offline methods.\nPromotions are rule systems, not scattered UI calculations.\nNotifications are event-driven and separate from delivery providers.\nAnalytics use metric definitions, date ranges, filters and drill-down rather than decorative charts.\nBeauty personalization works best when recommendations are connected to the shopper's stated goals and the reasons for the recommendations are understandable.\n\n5. VELORA ADAPTATION\n\nMarketplace order graph\nKeep the existing order → order_items → store/seller → shipment → shipment_items graph.\nDo not create a second order model.\n\nFulfillment\nKeep the existing shipments, shipment_items and shipping_carriers contracts.\nProvider integrations should be adapters around the existing shipment contract.\n\nSeller Center\nUse existing seller pages and RPCs. Map them to the mature task groups instead of adding a second seller backend.\n\nAdmin\nUse the existing Admin platform and operational sections. Add only a missing navigation or control surface when a real operational gap is observed.\n\nReturns\nKeep returns, return_items, disputes and governed RPCs. Build only the split-aware customer workflow that the current backend actually requires.\n\nPromotions\nKeep rules backend-authoritative. Avoid hard-coded frontend discount math.\n\nBeauty layer\nKeep Beauty Passport → Routine → Explain why → Shop routine as the differentiated Velora layer.\n\nRegion\nCountry context should determine exposed currency and operational methods. Egypt Restore-Test currently maps to EGP.\n\n6.
