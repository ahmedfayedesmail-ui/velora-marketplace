## 1. Phase A Decision Summary

The Beauty MVP will use exactly four new domain tables:

1. `beauty_profiles`
2. `recommendation_runs`
3. `recommendation_items`
4. `beauty_feedback`

Existing commerce tables remain authoritative:

- `profiles`
- `products`
- `product_variants`
- `carts`
- `cart_items`
- `orders`
- `order_items`

No duplicate customer, product, cart, order, or variant model will be introduced.

---

## 2. Table A — beauty_profiles

### Purpose

Persistent Beauty Passport owned by one authenticated customer.

### Proposed contract

| Column | Type | Required | Notes |
|---|---|---:|---|
| `user_id` | uuid | yes | PK; FK to `profiles.id` / Auth identity |
| `quiz_version` | text | yes | Versioned questionnaire contract |
| `goal` | text | yes | Explicit beauty/shopping goal |
| `concern` | text | yes | Explicit product concern/preference |
| `texture_preference` | text | no | Controlled preference |
| `effect_preference` | text | no | Controlled preference |
| `avoidance_preferences` | jsonb | no | Product-attribute exclusions only |
| `shopping_priority` | text | no | Controlled shopping preference |
| `updated_at` | timestamptz | yes | Server timestamp |

### Ownership

One active row per authenticated customer.

The client cannot choose another customer's owner identity.

### Non-goals

Do not store:

- diagnosis
- medical/clinical classification
- inferred health status
- medical advice

## 3. Table B — recommendation_runs

### Purpose

Records one deterministic recommendation calculation.

| Column | Type | Required | Notes |
|---|---|---:|---|
| `id` | uuid | yes | PK |
| `user_id` | uuid | yes | FK to `beauty_profiles.user_id` |
| `ruleset_version` | text | yes | Versioned scoring contract |
| `input_snapshot` | jsonb | yes | Sanitized Passport inputs used for the run |
| `created_at` | timestamptz | yes | Server timestamp |

### Ownership

The run belongs to exactly one authenticated customer.

### Write model

Customer reads own runs.

Run creation should occur through the canonical recommendation operation/RPC so the server derives the owner from the authenticated session and controls the ruleset version.

---

## 4. Table C — recommendation_items

### Purpose

The five ranked products generated by one recommendation run.

| Column | Type | Required | Notes |
|---|---|---:|---|
| `id` | uuid | yes | PK |
| `run_id` | uuid | yes | FK to `recommendation_runs.id` |
| `product_id` | uuid | yes | FK to canonical `products.id` |
| `product_variant_id` | uuid | no | FK to `product_variants.id` |
| `position` | smallint | yes | 1–5, unique per run |
| `score` | numeric | yes | Deterministic score |
| `reason_codes` | text[] | yes | Explanation source |
| `created_at` | timestamptz | yes | Server timestamp |

### Invariants

- `position` is unique within a run.
- visible recommendations are limited to five.
- every visible item has at least one reason code.
- `product_id` is always a canonical UUID.
- variant identity is preserved when the recommendation depends on a variant.

### Write model

Customer reads only their own recommendation items through ownership inherited from the parent run.

The browser should not directly be allowed to write arbitrary recommendation results.

---

## 5. Table D — beauty_feedback

### Purpose

Private personalization signal describing the customer's product experience.

This is intentionally separate from the existing public `reviews` table.

| Column | Type | Required | Notes |
|---|---|---:|---|
| `id` | uuid | yes | PK |
| `user_id` | uuid | yes | FK to `profiles.id` |
| `product_id` | uuid | yes | FK to `products.id` |
| `product_variant_id` | uuid | no | FK to `product_variants.id` |
| `order_item_id` | uuid | no | FK to `order_items.id` |
| `rating` | smallint | yes | 1–5 |
| `texture` | text | yes | Controlled feedback value |
| `effect` | text | yes | Controlled feedback value |
| `source` | text | yes | e.g. purchase / interaction |
| `idempotency_key` | text | yes | Unique per submission |
| `created_at` | timestamptz | yes | Server timestamp |
| `moderation_status` | text | yes | Internal moderation state |
| `moderation_note` | text | no | Staff-only moderation note |
| `moderated_by` | uuid | no | Staff actor |
| `moderated_at` | timestamptz | no | Staff action timestamp |

### Key boundary

Customers own their feedback.

Staff moderation is an operational capability and should not allow staff to impersonate the customer or rewrite the customer's factual submission.

Preferred implementation:

- customer INSERT/SELECT own feedback;
- staff reads moderation queue;
- staff moderation writes are performed through a narrow RPC that changes only moderation fields;
- no direct public update/delete of customer feedback.

## 6. RLS Matrix

| Table | anon | authenticated customer | staff |
|---|---|---|---|
| `beauty_profiles` | none | SELECT/INSERT/UPDATE own | explicit operational read only if required |
| `recommendation_runs` | none | SELECT own | explicit operational read if required |
| `recommendation_items` | none | SELECT items belonging to own runs | explicit operational read if required |
| `beauty_feedback` | none | SELECT/INSERT own | SELECT moderation queue + narrow moderation RPC |

### Customer ownership expression

The canonical row ownership pattern is:

`(select auth.uid()) = user_id`

For child tables whose owner is inherited through a parent:

`EXISTS (SELECT 1 FROM recommendation_runs r WHERE r.id = recommendation_items.run_id AND r.user_id = (select auth.uid()))`

RLS must be enabled on all four public tables.

Indexes should be added for policy join/filter keys, especially:

- `beauty_profiles.user_id`
- `recommendation_runs.user_id`
- `recommendation_items.run_id`
- `beauty_feedback.user_id`
- `beauty_feedback.order_item_id`
- `beauty_feedback.product_id`

## 7. Existing Model Integration

### 7.1 orders → beauty_feedback

**Yes — optional purchase link.**

`beauty_feedback.order_item_id` points to the exact purchased line item.

The backend must validate that:

1. the order item belongs to the authenticated customer;
2. the supplied `product_id` matches the order item;
3. the supplied `product_variant_id`, when present, matches the order item;
4. the feedback idempotency key has not already been used.

This prevents a customer from submitting feedback against another customer's purchase record.

### 7.2 products → Beauty Passport matching

**Yes — but as matching logic, not as a foreign-key relationship.**

The Rules Engine reads the user's explicit Passport fields and the canonical product attributes.

Primary product signals:

- `category`
- `subcategory`
- `skin_types`
- `concerns`
- `tags`
- `benefits`
- `ingredients`
- `price` / `currency_code`
- availability / status

The Passport should not contain a permanent list of product IDs just to represent preferences.

### 7.3 product_variants → recommendations/cart

Variant identity remains canonical:

`product_id + product_variant_id`

The recommendation engine may select a specific active variant when the product cannot be purchased meaningfully without it.

## 8. Rules Engine Contract

Phase A fixes the data boundary; Phase B can implement the scoring.

Initial deterministic scoring contract:

| Signal | Weight |
|---|---:|
| Goal match | 40 |
| Concern match | 25 |
| Texture match | 15 |
| Effect match | 10 |
| Preference / avoidance alignment | 10 |

Total = 100.

This is an engineering baseline, not a commercial decision.

Reason codes must be persisted alongside the score.

## 9. API / RPC Boundary

The exact physical function names remain implementation decisions, but the logical operations are fixed:

1. load current Beauty Passport
2. save current Beauty Passport
3. calculate recommendations
4. load current recommendation history
5. submit Beauty Feedback
6. moderate Beauty Feedback

The authenticated identity should be derived from the active Supabase Auth session.

Do not accept a client-selected `user_id` as an authorization decision.
